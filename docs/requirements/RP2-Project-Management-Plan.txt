I. Project Overview
1. Scope and Purpose 
TK Sport Community (TKSC) is a website developed by group G138 for TK Sport. It manages badminton and pickleball social sessions, separate counter sales, session supplies and reconciliation. Both sports share a workflow but retain separate assessment records.
TK Sport has about 20–30 participants each day. The venue operates from Monday to Sunday in three time slots: 16:00–18:00, 18:00–20:00, and 20:00–22:00. Each slot uses two courts with two assigned referees. The courts may serve different skill groups.
The project aims to reduce skill mismatches and manual management tasks. Players receive suggestions for sessions that match their skill level. Organizers track profiles, registrations, and payments in one system.
This report plans FE-01–FE-18 in Report 1. It distinguishes project-team responsibilities from the venue roles. Trần Minh Đức is the team leader and provides initial System Admin support; Lâm operates as Manager. The court owner uses the Owner role.

Added role, sales and stock work uses the original capacity allowance.

Reduced contingency can delay core flows or final verification.
Track EX estimates separately, review member workload each week and keep the 05 October document milestone. Do not hide scope growth inside old effort totals.
R02
Referees give inconsistent scores, or new players overstate their skill level.

Players are placed in unsuitable sessions.
Agree on criteria for each sport. Mark provisional scores and compare different assessments. Lâm and the referees handle complaints.
R03
A place is confirmed twice, or entry rules are checked incorrectly in group registration.

Sessions exceed capacity or accept players who do not meet the rules.
Recheck each player’s level, available places, and status at confirmation. Test several registration requests at the same time.
R04
A payment, sales handover, refund or stock movement is duplicated or linked to the wrong record.

Ticket status, amounts, or refund recipients are incorrect.
Test source-event uniqueness, separate social/sales references, repeated delivery, last-item conflicts and independent physical returns/refunds. Keep unresolved amounts visible.
R05
Users view or edit data beyond their access rights.

Internal comments are exposed, or scores, tickets, and payments are changed incorrectly.
Test one role per account and the underlying person link. Block System Admin rating decisions and self-approval; keep technical, financial and assessment histories separately controlled.

6.2. Source Code Management
The project source code is managed with Git and stored on GitHub. The group uses two types of branches:
master branch: Contains stable code that is ready to deploy.
feature branches: Each feature or bug fix is developed on a separate branch before it is merged into master. The branch name briefly describes the task, for example: feature/player-assessment.
Each commit has a short, clear message that accurately describes the change. Example: feat: add referee skill assessment.
After finishing the work, the developer checks it and creates a pull request. At least one other team member must check, review, and approve it before it is merged into master. The author makes any requested changes on the same working branch.
This process helps the group work together, reduces code conflicts, and checks quality before deployment.
Each test version and each version used at the venue has its own version number. The group keeps the deployment documents and test results with it. When fixing a defect during the trial, the group records the previous version, the new version, and the changes to compare with feedback.
